# Existing Apple USB4 work, and what applies to the T6034

Research for hungbenjamin402/linux-aurora#3, part of the map in #1. Target: the J516M (16" M3 Max, T6034), whose device tree is `t6034.dtsi` on top of `t6031.dtsi`. Terms follow `wayfinder/usb4-m3max/GLOSSARY.md`.

Sources are the `usb4-m3max` branch (the J516M kernel, 29 commits on top of `integration/aurora` 8eddf5aeb6ac, among them the merge of omacom PR #292), `origin/integration/aurora` (omacom/linux-aurora), aurora-silicon/linux, AsahiLinux/linux, and the upstream mailing-list record. Commit hashes are omacom/linux-aurora commits (all present in this repo) unless the row says aurora-silicon/linux. **(inference)** marks a conclusion that the sources do not state directly.

## The finding that changes the plan

The DP-in qualification that the branch already carries for the M3 Max never runs on the J516M. PR #292 (`abbc8264bc0b`) adds `apple,t6031` to `apple_dpin_qualified_soc` and adds `of_machine_is_compatible("apple,t6031")` checks in `atc.c` and `dcp-fabric.c`. But the J516M root node is `"apple,j516m", "apple,t6034", "apple,arm-platform"`: `t6034.dtsi` replaces the root compatible, and `/proc/device-tree/compatible` on this machine confirms it. So:

- the ACIO does get PR #292's `apple_cio_t6031_hw`, because the J516M ACIO nodes come from `t6031-dieX.dtsi` and carry `apple,t6031-usb4-acio`;
- `apple_dpin_policy_select()` still returns `apple_dpin_disabled`, because the root does not match;
- the T6030 tunnel-clock and crossbar paths in `atc.c` and `dcp-fabric.c` stay off.

Open PR omacom #406 (BTNG-studio, J516M) fixes exactly this. It adds `apple_dp_tunnel_m3_soc()` (T6030 or T6034) and puts `apple,t6034` on the qualified list. It conflicts with #292 on the `apple_cio_t6031_hw` hunk: #406 leaves T6031 disabled, while #292 enables it.

#406 also contains a fact that matters for the NHI bring-up ticket. On another J516M (m1n1-aurora `1.6.1.aurora22-103`, kernel `7.2.11.aurora14-107`), the log shows `thunderbolt 0-1: Apple Inc. Studio Display`, and the commit message says "the Thunderbolt link to a display comes up and its DP tunnels are created". So the NHI bound and a USB4 domain came up on a T6034 using the stock driver, with the ACIO matching the `apple,t8103-usb4-acio` fallback. That contradicts the map's starting fact that no NHI binds on this machine. The difference is likely in m1n1 or the boot chain (for example the DROM, which `t6031-dieX.dtsi` leaves as `[00]` for the loader to fill) and not in the driver **(inference)**.

## Notes

1. **No PCIe or USB3 tunnel work exists for any M3 Max.** Everything on the T6031/T6034 side is DP tunnel and display work. T6030 has one PCIe tunnel port. The spec's tunnel slices start from the T6030 port-0 template with J516M ADT values.
2. **`t6034.dtsi` drops `apple,t6031` from the root compatible.** Any `of_machine_is_compatible("apple,t6031")` or root-match check written for the J516C misses the J516M. Two ways out: match on the T6031 *block* compatibles (the ACIO, ATC and crossbar all carry `apple,t6031-*`), or add `apple,t6034` everywhere, as #406 does. Ask upstream which they prefer before writing the slice.
3. **The ACIO start does not need T6030's MxWrap path.** The T6031 node has no `cpu` reg, and a J516M link came up with the t8103 start (#406).
4. **PR #188's eGPU fixes need no T6034 code changes** beyond identity `ranges` in the new tunnel nodes, and confirming the root-port prefetchable enable works on `apple,t8122-pciec` hosts (it was measured only on T6001 and T6021) **(inference)**.

- I did not check m1n1 (omacom/m1n1, AsahiLinux/m1n1) for T6031/T6034 USB4 handling: DROM fill, `usb4_N_*` alias consumers, ACIO/DART tunables. The #406 J516M result points there for the NHI-bind gap.
- I found no T6031/T6034 USB4 work in aurora-silicon/linux or AsahiLinux/linux beyond what this tree already has. Private or unpushed branches cannot be ruled out.
- PR #406 was compile-tested after its rebase but not booted; its booted run was on an older #372 head.
